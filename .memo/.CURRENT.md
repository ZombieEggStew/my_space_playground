## 2. 目标架构

### 2.1 核心原则:模块 = 能力 + 该能力 UI 的所有者

> **装模块 → 获得能力(含其 HUD);卸模块 → 能力连同 UI 一起消失,无泄漏、无残留。**

- `HUDManager` 只是**渲染层注册中心**:决定元素挂 static/far/group 哪一层 + 统一特效合成。
- 能力模块负责自己能力的 UI **组装与生命周期**("UI 控制器"从全局外置 → 模块内嵌 `xxx_compat`)。
- 跨模块**状态**走通信层(§2.2);模块内部(父↔子)走树内直连。

**判别规则(节点归属依据)**:
- **玩家固有属性**(不依附任何玩法模块就存在):血量、速度、buff 状态 → **module_hud** 显示,Stat 绑定。
- **模块能力相关**(只有装了模块才存在):目标(radar)、能量(booster)、热量(laser)、护盾(shield)、
  瞄准/预测准星(aim/predict)→ **各模块自持**。
- 数值面板(Stat 驱动)→ 可集中 module_hud;动态元件(每帧位置/几何由玩法驱动)→ 留在玩法模块。

### 2.2 三级通信模型

| 级别 | 载体 | 管什么 | 判定规则 |
|---|---|---|---|
| ① 模块内部 | 树内直连信号 | `xxx_compat` ↔ 玩法逻辑、父↔子 | 收发双方在同一模块树内 |
| ② 飞船级 | `ShipBus`(船上节点,`class_name ShipBus`) | 同船兄弟模块间的输入/状态(aim→predict/missile 等) | 收发双方是同一艘船的兄弟模块 |
| ③ 世界级 | 全局 `SignalBus`(autoload) | 目标 spawn/died、伤害、玩家注册等"世界实体"事件 | 不依附任何一艘船的事件 |

纪律(两级总线通用):**只声明信号,零逻辑零状态**;"当前值"存模块/Stat,bus 只发"变化"脉冲。

**现有 SignalBus 信号归类草案**(迁移视图,雷达机制定稿后可微调):

| 信号 | 归到 |
|---|---|
| `on_player_registered` / `on_lockable_target_spawned` / `on_lockable_target_died` / `on_damage_dealt` | ③ 世界级 |
| `on_player_try_lock` / `on_player_boost_input` / `on_toggle_engine` / `on_toggle_track_mouse` / `on_player_look_backward` / `on_player_look_around` / `on_player_try_use_item_1` / `on_player_boost` / `on_player_shoot` / `on_player_lock_target` | ② 飞船级 ShipBus |
| `on_target_hovered` / `on_target_unhovered` | ① 移除,aim 树内直连 |

### 2.3 命名约定

- 跨模块边界的内容统一 `xxx_compat`(如 aim 的 UI 子模块 → `aim_compat`;radar 的 UI → `radar_compat`)。
- `ShipBus` 为飞船级总线节点;全局 `SignalBus` 只留世界级信号。

### 2.4 模块系统:身体/能力 与 大脑/决策 分离(2026-09-07 定案)

**动机**:现状"同一艘船怎么动/怎么打"有两套并行系统——玩家侧模块直接读 `Input`
(`module_move_controller` 读按键/鼠标,booster 听 `on_player_boost_input`);敌人侧
`AIBrain`+`MoveSM`(自实现移动)+`CombatSM`/`state_attack`(自 spawn 子弹,目标硬编码玩家)。
重构为:一份共享实现 + 两种大脑。

```
玩家输入(键鼠/手柄) ─┐
                      ├─→ 归一化命令 → 共享模块(engine/booster/weapon/radar…)
敌人 AI 决策        ─┘   set_throttle(0..1) / set_steer(Vector2) /
                         set_boosting(bool) / set_firing(bool) / set_aim_dir(Vector3)
```

**命令接口原则**:模块只懂命令、不懂意图(前进键与 AI 追击在模块看来都是 `set_throttle(1.0)`)。
载体(决策 #12):连续量=直接方法,离散事件=ShipBus 信号;大脑对未装模块空指针降级。

**模块分类**:

| 模块 | 类别 | 说明 |
|---|---|---|
| engine/move | 共享 | `set_throttle`/`set_steer`;鼠标跟随转向迁入 ControlModule(决策 #13) |
| booster | 共享 | `set_boosting(bool)` 替代听 `on_player_boost_input` |
| laser / missile | 共享 | `set_firing(bool)` + `set_aim_dir()`;子弹 team_id 取自 `root.get_team_id()`(已中立) |
| radar | 共享 | 机制见 §4.1;敌人 AI 用它选目标,消除"目标=玩家"硬编码 |
| shield / heat | 共享 | 无输入耦合,天然共享 |
| aim_mechanics | 共享 | 决策 #11:给定目标算预测点/驱动准星;target_selection(选谁打)在大脑侧 |
| camera(third_camera) | 玩家独有 | 敌人不需要第三人称相机(AI 用 radar + 直接读节点) |
| module_hud / xxx_compat | 玩家安装 | 敌人不装显示;数据在共享组件(HealthComponent 等) |
| **ControlModule** | 玩家独有 | 键鼠/手柄 → 归一化命令 |
| **AIModule** | 敌人独有 | 状态机保留在内部,输出归一化命令;删 MoveSM/CombatSM 重复实现(决策 #14) |

**迁移顺序**(决策 #16):①共享模块逐个加命令接口,玩家侧改经 ControlModule 调(行为不变,纯搬运)
→ ②敌人侧 AIModule 改造,删重复逻辑 → ③装配组合验证(玩家/敌人装不同模块组合)。

## 4. 设计定案与待定项

### 4.1 雷达机制 ✅ 已定(2026-09-07)

- **定位**:敌我飞船**直接复用**的模块;装了就决定该船**视野范围**(半径 R 球形),提供视野内所有可侦测目标。
- **信息源**:③世界级 `on_lockable_target_spawned/died` 事件(增量)+ **"detectable" 组快照**
  (`AbleToBeLocked` 进组;radar 用 `get_tree().get_nodes_in_group("detectable")` 拉全量,支持中途装卸/重装同步)。
- **半径过滤**:radar 内部按 `root.global_position.distance_to(target) <= detection_radius` 过滤
  (`@export detection_radius`,敌我同一套逻辑);维护"视野内"集合,进出视野各发一次事件。
- **过滤频率**:事件驱动 + 每帧距离检查;实现从简(快速迭代,随时可改)。
- **发布契约**:只发布**身份 + 生命周期** — `on_target_entered(target)` / `on_target_exited(target)` +
  `get_targets_in_range()`;具体状态(3D 坐标/血量/速度)消费方**从目标节点直接读**;
  **2D 屏幕坐标不在 radar 算**(相机相关,谁用谁 unproject);阵营过滤由消费方做(radar 给全量 + 各目标 `team_id`)。
- **对称性前提**:玩家飞船也要挂 `AbleToBeLocked`,否则敌人雷达侦测不到玩家(顺带解锁"玩家被锁定"玩法)。
- **"可侦测"规则扩展**:放 `AbleToBeLocked` 组件(组件自报是否可侦测),radar 只管半径。

### 4.2 待定项

1. **目标选择框归属**:随 radar(与目标血条一起)还是留 aim 的 aim_compat。
2. **aim 无 radar 时降级策略**:无目标来源时,`Log.log_missing_component` + 禁用相关功能(推荐),
   还是 `queue_free` 整个 aim 模块。
3. **module_hud 与 `module_basic_info_ui` 的关系**:改名,还是做成真正的"玩家状态显示模块"。
4. **aim_compat 职责边界**:aim 拆两层(决策 #11)后,aim_compat 归属 aim_mechanics 还是 selection;
   拥有哪些 2D 节点、与玩法部分的接口、卸载清理路径(依赖待定项 1)。
5. **卸载 API**:`ModulesManager` 目前只有 `install_*`,需补 `uninstall_module`(queue_free + 清类型槽),
   且 GROUP 元素(reparent 到 hud_container 的容器)不会随模块释放,需要卸载清理方案。
6. **InputManager 位置(决策 #15)**:历史做法是外置全局;疑似鼠标检测放玩家内部会被某层消耗/阻挡,
   需查证原因后定:ControlModule 直接读 `Input`,还是 InputManager 变薄成硬件抽象层喂给当前玩家。
